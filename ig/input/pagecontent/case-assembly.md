本頁定義「收錄資料說明」中的個案組裝規則：從醫院的癌登長表記錄，決定哪些**腫瘤**（一筆登記個案＝一個原發大腸癌 Condition）進入指標計算，並為每個被排除的腫瘤給出一個可機讀的排除原因。

先前版本把「院內重複個案」、「治療前已死亡」與「外院資料」交給未定義的 Task 層處理。這會讓兩家醫院對同一份資料算出不同的分母，因此本頁把演算法寫成確定的步驟，並提供參考實作 `reference/cohort.py` 與測試 `tests/test_cohort.py`。兩者與本頁不一致時，以本頁為準並修正程式。

來源：「115 年癌症診療核心測量指標」壹、收錄資料說明（第 i–ii 頁）；「附件2_大腸癌診療公告指標」；臺灣癌症登記長表 FHIR IG（套件 `fhir.TWCRLF` 0.1.1，以下稱 TWCR_LF）。本頁另需的長表欄位列於 `mappings/case-assembly-fields.csv`。

### 標示說明

- **【原文】**：國健署文件逐字引用。
- **【本 IG 決定】**：原文沒有寫明，本 IG 採用的做法。每一項都列在文末「待國家衛生研究院確認」。
- **旗標（flag）**：不影響是否納入，只標記該筆記錄的結果用到了本 IG 的決定，方便稽核。

### 處理順序

每個腫瘤只得到一個排除原因：依下表順序，第一個不符合的步驟即為原因。

| 步驟 | 規則 | 排除原因代碼 | 預計位置 |
|---|---|---|---|
| 1 | 癌別為大腸癌 | `NOT_COLORECTAL` | CQL（已實作） |
| 2 | 2.5 為有效日期 | `INVALID_DIAGNOSIS_DATE` | CQL（已實作） |
| 3 | 2024-01-01 起新診斷，且在 Measurement Period 內 | `DIAGNOSIS_BEFORE_2024`、`OUTSIDE_MEASUREMENT_PERIOD` | CQL（已實作） |
| 4 | 重複個案 key 完整（1.1 申報醫院代碼） | `MISSING_DEDUP_KEY` | CQL（已實作） |
| 5 | 院內重複個案（註 1） | `DUPLICATE_OF:<保留的 tumour_id>` | CQL（已實作） |
| 6 | class 1、2 | `CLASS_NOT_1_OR_2` | CQL（已實作） |
| 7 | 跨院治療（註 3） | `CROSS_HOSPITAL_TREATMENT` | CQL（已實作） |
| 8 | 治療前已死亡 | `DIED_BEFORE_TREATMENT` | CQL（已實作） |
| 9 | 外院資料（第五點，逐指標） | `OUTSIDE_DATA_BOTH`、`OUTSIDE_NUMERATOR_NOT_OBTAINED` | **醫院提供的輸入** |

**【本 IG 決定】步驟 1–3 在去重之前，步驟 6–9 在去重之後，只對保留下來的代表記錄判定。** 理由：國健署要求的申報範圍是「自 113 年 1 月 1 日起新診斷個案」，註 1 是在這個範圍內為每個「人＋癌別」挑出一筆代表。代表記錄若因 class、跨院或死亡被排除，不會改由同一人的另一筆記錄遞補；否則同一個病人可能因備用記錄而被計入，結果也會隨記錄順序而變。

### 規則 1：癌別

【原文】註1：「重複個案定義：指同一醫院內重複癌別之個案　醫院代碼＋癌別＋身分證號」。

原文沒有定義「癌別」的代碼範圍。本 IG 的判定（`cancer_category`）：

| 原發部位 (2.6) | 癌別 | 依據 |
|---|---|---|
| C18.0、C18.2–C18.9 | 大腸癌 | 指標文件「三、大腸癌診療」；指標 2 部位＝Colon (C18) |
| C19.9、C20.9 | 大腸癌 | 同一章、同一「指標群組：大腸癌」；指標 3 部位 C19-20 |
| C18.1（闌尾） | 非大腸癌（旗標 `APPENDIX_C181_EXCLUDED`） | 附件2「適用範圍：結腸癌 (Colon)：ICD-O-3 編碼為 C18.0 - C18.9（不包含 Appendix C18.1）」 |
| C21.x（肛門、肛管） | 非大腸癌（旗標 `ANUS_C21_EXCLUDED_PENDING_CONFIRMATION`） | 國健署 115 年文件沒有任何地方提到 C21 |
| 其他 | 非大腸癌 | — |

**【本 IG 決定】結腸（C18）與直腸（C19–C20）屬同一個癌別「大腸癌」。** 依據：(1) 兩者在指標文件中同屬「三、大腸癌診療」，指標群組都寫「大腸癌」；(2) 附件2 的 SSF9 說明提到「同步結直腸癌」，把同時發生的結腸與直腸原發視為同一疾病群。反面考量：癌登部位特定因子（SSF）對結腸與直腸分別編碼（TWCR_LF 有 `ssf-*-colon` 與 `ssf-*-rectum` 兩組代碼系統），但那是摘錄規則，不是指標癌別。

後果：同一醫院同一病人同時有結腸癌與直腸癌時，只保留一筆。若保留的是直腸癌，結腸癌就不會進入指標 2 的分母。這是字面解讀的結果，列為待確認事項。

### 規則 2–3：診斷日期與收錄期間

【原文】第一點：「各癌症診療測量指標收錄對象為自 113 年 1 月 1 日起新診斷個案。」

- 2.5 不是有效日期 → `INVALID_DIAGNOSIS_DATE`。**【本 IG 決定】** 這類記錄在去重前就排除，不參與「選診斷早者」的比較（無法排序，也一定不符合第一點）。
- 2.5 早於 2024-01-01 → `DIAGNOSIS_BEFORE_2024`。
- 呼叫端指定 Measurement Period 時，2.5 不在期間內（含首尾日） → `OUTSIDE_MEASUREMENT_PERIOD`。

**【本 IG 決定】** 期間外的記錄不進入去重範圍。因此 2023 年在本院已有大腸癌、2024 年又登記一筆大腸癌的病人，2024 年那筆不會被判為重複。

### 規則 4–5：院內重複個案（註 1）

【原文】註1：「重複個案定義：指同一醫院內重複癌別之個案　醫院代碼＋癌別＋身分證號（選診斷早者，若同一天選期別嚴重者）。」

演算法：

1. 原文 key 為（1.1 申報醫院代碼, 癌別, 1.4 身分證統一編號）；本 IG 中 1.4 由 Patient 代表、不參與比對（見本步驟後段）。識別碼先去除前後的半形空白與 tab 並轉為大寫（內含空白不移除，視為不同的值；CQL 與參考實作一致）。只由空白字元組成的值（含全形空白、換行）視為空，規則見[收錄條件](inclusion-rules.html)。1.4 的 `9999999999` 在長表中表示「個案無身分證統一編號」（摘錄手冊第 56 頁）；參考實作直接呼叫 `assemble_cohort` 時視同空值。**同一人的判定【本 IG 決定】**：CQL 在 Patient context 中執行，同一次評估的所有腫瘤都屬於同一個 Patient 資源，因此「身分證號相同」由 Patient 本身代表，1.4 不參與比對。1.4 缺漏或為 `9999999999` **不排除**個案（早期版本會以 `MISSING_DEDUP_KEY` 排除，但那只讓個案消失，並沒有換來任何去重效果）。代價是：同一人若分散在兩個 Patient 資源，CQL 無法合併，送進評估前必須先完成病人身分整合（見[收錄條件](inclusion-rules.html)「一人一個 Patient」）。1.1 參與比對，空白時 → `MISSING_DEDUP_KEY`。參考實作 `assemble_cohort` 以傳入的 `patient_id` 代表同一人，本 IG 的測試以 Patient 資源代入；直接呼叫時 `patient_id` 空白仍為 `MISSING_DEDUP_KEY`。不得以 1.2 病歷號碼代替 1.4。1.4 只認 `Patient.identifier` system `http://www.moi.gov.tw`（身分證）：摘錄手冊規定 1.4 為身分證統一編號，且「收案對象為中華民國國籍(外籍人士不收案)」，居留證號（TW Core `http://www.immigration.gov.tw`）、護照號碼不是 1.4。
2. 每個 key 只保留一筆，其餘記錄的原因為 `DUPLICATE_OF:<保留的 tumour_id>`。
3. 保留 2.5 最早者。【原文】
4. 2.5 同一天時，保留期別較嚴重者。【原文】期別的取法與排序見下。結果加旗標 `SAME_DAY_TIE_BROKEN_BY_STAGE`。
5. 期別仍相同（或兩者都無法排序）時，保留 `tumour_id` 字串最小者，加旗標 `TIE_BROKEN_BY_TUMOUR_ID`。**【本 IG 決定】原文未涵蓋此情形**；這只是為了讓結果確定、與輸入順序無關。

**比較用的期別【本 IG 決定】**：先用病理期別組合 3.13；3.13 無法排序（`888`、`999`、空白等，例如未切除）時，改用臨床期別組合 3.7（旗標 `STAGE_FROM_CLINICAL_FALLBACK`）；兩者都無法排序時，該筆排在所有可排序期別之下（旗標 `STAGE_UNRANKABLE`）。依據：說明檔第七點「其指標中所指之分期，除非個別指標特有所指，否則一般乃係指病理分期」。第七點原本針對涉及手術、病理的指標，註 1 是共通規則，沿用第七點是本 IG 的類推。

**期別嚴重度排序【本 IG 決定】**（由輕到重；代碼取自 TWCR_LF `CliStageGroup`／`PathStageGroup`）：

```
0 < 0A < 0IS
< 1 < 1A < 1A1 < 1A2 < 1A3 < 1B < 1B1 < 1B2 < 1C < 1E < 1S
< 2 < 2A < 2A1 < 2A2 < 2B < 2BU < 2C < 2E
< 3 < 3A < 3A1 < 3A2 < 3B < 3C < 3C1 < 3C2 < 3D
< 4 < 4A < 4A1 < 4A2 < 4B < 4C
```

- 主期別 0 < I < II < III < IV；同一主期別內，只記主期別（未記次分期）者排在其次分期之下，之後依字母 A < B < C < D、再依數字。
- 大腸癌 AJCC 第 8 版實際會用到的只有 0、1、2A、2B、2C、3A、3B、3C、4A、4B、4C；其餘代碼只是為了讓排序完整。
- 無法排序：`OC`、`888`（不適用）、`999`（不清楚或醫師未記錄）、`BBB`、空白、其他值。

### 規則 6–7：個案分類與跨院治療

【原文】第三點：「選取個案分類為 class 1、2 者」；註3：「跨院治療：若個案分類 class 2，診斷狀態 2，治療狀態分類 3（他院診斷，於申報醫院接受部份首次療程，也於他醫院接受部份首次療程。排除）」。

- 2.3 不是 `1` 或 `2`（含空白） → `CLASS_NOT_1_OR_2`。
- 2.3＝`2` 且 2.3.1＝`2` 且 2.3.2＝`3` → `CROSS_HOSPITAL_TREATMENT`。三者缺一不排除。
- 指標 3 另有「僅納入 class 1」的專屬條件，屬於分母定義，不在本頁處理。

### 規則 8：治療前已死亡

【原文】第二點：「排除院內重複個案（註 1）、治療前已死亡及主要治療（註 2）有跨院情形（註 3）。」原文沒有指定判定欄位。

本 IG 使用的欄位（出處見 `mappings/case-assembly-fields.csv`）：

- **5.3 最後聯絡或死亡日期**（TWCR_LF `outcome.dateOfLastContactOrDeath`）。只有 5.4 表示死亡時，5.3 才視為死亡日期；否則是最後聯絡日期。
- **5.4 生存狀態**（TWCR_LF `outcome.vitalStatus`，對應 `Patient.deceasedBoolean`，「記錄個案『最後聯絡或死亡日期』的存活狀態」）。長表摘錄手冊（民國 114 年版）第 314 頁：編碼範圍 0–1，**`0`＝死亡、`1`＝存活**。TWCR_LF 套件把 5.4 對應到 `Patient.deceasedBoolean`，但本 IG 保存的是長表原始值，CQL 與參考實作都以 `0` 判定死亡。其他值（例如 `true`、`9`）視為「不知是否死亡」（參考實作旗標 `VITAL_STATUS_UNRECOGNISED`），不據以排除。
- **2.3.2 治療狀態分類代碼 0**：「未於申報醫院接受任何治療即死亡：(1)申報醫院診斷後死亡或病危出院 (2)他院診斷，轉診至申報醫院後死亡」。

**【本 IG 決定】判定規則**：符合下列任一項 → `DIED_BEFORE_TREATMENT`。

| | 條件 | 旗標 |
|---|---|---|
| (a) | 2.3.2＝`0` | `DIED_BASIS_TX_STATUS_0` |
| (b) | 5.4＝死亡，且 4.1＝`00000000`（無首次療程），且 2.3.2 ≠ `4` | `DIED_BASIS_DEAD_AND_NO_FIRST_COURSE` |
| (c) | 5.4＝死亡，5.3 與 4.1 都是有效日期，且 5.3 早於 4.1 | `DEATH_DATE_BEFORE_FIRST_COURSE_DATE_INCONSISTENT` |

不排除、但加旗標的情形：

- 5.4＝死亡且 5.3 與 4.1 同一天：當天已開始治療，視為「治療後」死亡（旗標 `DEATH_ON_FIRST_COURSE_DATE`）。
- 5.4＝死亡，但 4.1 或 5.3 為 `99999999`、`00000000`（5.3）、空白或無效日期，且 (a)、(b) 都不成立：無法確定先後，不排除（旗標 `DEAD_BUT_DEATH_OR_TREATMENT_DATE_UNKNOWN`）。

說明：

- (a) 是長表中唯一直接寫明「未接受任何治療即死亡」的代碼。它也包含「病危出院」，因此即使 5.4 記為存活也會排除；這一點需要確認。
- (b) 排除 2.3.2＝`4`（首次療程為「不予治療或是再密切觀察」或僅緩和照護）：這類病人的首次療程就是「不治療」的決定，之後死亡不屬於「治療前」死亡。
- (c) 在邏輯上不應出現（死亡後不會開始治療），出現即表示資料有誤；依字面排除並加旗標，供醫院回頭檢查。
- 4.1.10＝5、4.2.1.8＝05、4.3.3／4.3.6／4.3.9／4.3.11／4.3.14＝85 等「因個案未接受治療前即死亡或病危出院」代碼不採用，因為死亡與病危出院合併編碼，無法單獨判定死亡，而且只針對單一治療方式。

### 規則 9：外院資料（第五點）

【原文】第五點：

> 1.分子與分母皆係屬外院資料：不列入指標之分子與分母中計算。
> 2.分子與分母分別係屬外院及院內的資料（1）病人在外院的資料是否納入指標中計算，乃取決於申報醫院是否能取得病人於外院接受相關處置的資訊。（2）若癌症個案係屬測量指標中分母所定義之對象，在分析時，能取得病人在外院的分子資料者，則必須納入指標之分子與分母中計算；若只知病人係屬指標分母所定義之對象，而無法取得外院分子資料，則不列入指標內計算。

**為什麼不能只從登記欄位判定**：

1. 規則依「申報醫院**是否能取得**外院資料」而定，這是醫院在分析當時的資料取得狀態，不是長表的任何欄位。
2. 某一筆長表值是醫院自行處置的結果，還是摘錄自外院資料，長表沒有逐欄記錄來源。2.3.1、2.3.2 只描述整個首次療程的分工，無法對應到某一指標的分子或分母。
3. 規則是**逐指標**的：同一個腫瘤可能指標 2 的分子資料（淋巴結檢查數目）在本院，指標 3 的分子資料在外院。

因此本 IG 不推測，而是由醫院對每個指標、每個腫瘤明確宣告。交換時以 [CRCOutsideDataExclusion](StructureDefinition-crc-outside-data-exclusion.html) 表達：只有要排除的腫瘤需要一筆宣告，`BOTH_OUTSIDE` 對應理由代碼 `both-outside`、`NUMERATOR_OUTSIDE_NOT_OBTAINED` 對應 `numerator-outside-not-obtained`；沒有宣告即為納入（`IN_HOSPITAL` 或 `NUMERATOR_OUTSIDE_OBTAINED`）。參考實作 `reference/cohort.py` 的 `outside_data` 參數接受以下狀態：

| 狀態 | 意義 | 結果 |
|---|---|---|
| `IN_HOSPITAL` | 分子與分母資料都在本院 | 納入 |
| `BOTH_OUTSIDE` | 分子與分母皆屬外院資料（第五點 1） | 排除，`OUTSIDE_DATA_BOTH` |
| `NUMERATOR_OUTSIDE_OBTAINED` | 分母屬本院、分子屬外院，且已取得（第五點 2(2) 前段） | 納入 |
| `NUMERATOR_OUTSIDE_NOT_OBTAINED` | 分母屬本院、分子屬外院，未能取得（第五點 2(2) 後段） | 排除，`OUTSIDE_NUMERATOR_NOT_OBTAINED` |

- 未提供 `outside_data` 時不套用本規則（產生的是各指標共用的基礎族群）。
- **【本 IG 決定】** 有提供對照表、但某個腫瘤不在表中時，視為 `IN_HOSPITAL`，並加旗標 `OUTSIDE_DATA_STATUS_NOT_SUPPLIED`，讓審查者看得到。
- 狀態值不在上表時，參考實作直接拋出錯誤，不猜測。
